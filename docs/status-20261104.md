# Status (2026-11-04)

Renderer numbers are LPIPS (AlexNet) and PSNR against the app's own 512 px GAGAvatar render of the same motion, on two clips (1,022 frames) and three avatars, one of them a training identity. Capacity numbers are from the real app in browser-rendering mode with headless clients on A100-80GB GPUs. Every number below was re-derived from the raw outputs by a separate check.

## 1. Results for the directions agreed on 2026-10-28

**Easy mode and professional mode: implemented. The app now opens on an easy view with an avatar gallery, labelled voices and START; the full controls are in a professional view, with detailed settings in a tab that is closed by default.**

- Easy view: a gallery of avatar thumbnails (made at runtime from each avatar's tracked data), a voice picker with a short description per voice, and START/STOP. It hides the diagnostics panels.
- Professional view: today's sidebar, opened by adding `?pro=true` to the app address. Backend, model, diagnostics and playback options sit in an Advanced tab that is closed by default.
- Voice labels use only what each provider publishes. OpenAI describes its GPT-Live voices (for example "masculine, North American English"), and those descriptions are shown; its older Realtime voices have no published description, so they show the name only rather than a guessed gender. xAI's and PersonaPlex's voices use their own published descriptors.
- The operator chooses which built-in avatars visitors see. Avatars a visitor registers from a photo appear in the gallery under the name the visitor gave them, and the form clears after registration.
- Session limit, queue, sign-in and feedback work as before in both views; checked headlessly with screenshots of both views, including browser-rendering mode.

**Rendering resolution, 256 vs 512 px and upsampling: the 256 px-core network with light sharpening is the recommended default. The 512 px network looks better (LPIPS 0.046 vs 0.054) but costs about 1.8x the frame time. Upsampling a 256 px image after the fact is clearly worse. On an M4 MacBook Air the 512 px network does not keep up at 25 fps, so the 256 px core is the right default there.**

- The 256 px-core network already outputs 512 px: it runs on the 256 px splat and ends in a learned 2x upsampling layer. So "256 plus upsampling" is what it does today, and the question is whether it is close enough to the 512 px network.

| against the 512 px GAGAvatar render | LPIPS mean | avatar 1 (training) | avatar 5 (held out) | avatar 9 (held out) |
|---|---|---|---|---|
| 256 px core (learned 2x output) | 0.0587 | 0.0329 | 0.0885 | 0.0548 |
| 256 px core + sharpening | 0.0540 | 0.0292 | 0.0849 | 0.0478 |
| 512 px network | 0.0482 | 0.0278 | 0.0702 | 0.0466 |
| 512 px network + sharpening | 0.0461 | 0.0265 | 0.0689 | 0.0430 |
| 256 px output, downscaled to 256 and upscaled again (bicubic / Lanczos) | 0.0821 / 0.0775 | | | |
| 256 px core + an extra learned sharpening layer | 0.0561 | | | |

- The ranking is the same on every avatar. On avatar 9 the gap between the 512 px network and the sharpened 256 px core is narrow (0.0466 vs 0.0478); on the harder held-out avatar 5 it is wide.
- Sharpening is an unsharp mask at strength 0.5. It costs 0.04 ms of GPU time per frame, too little to show in wall time, and lowers LPIPS for both networks on every avatar.
- The extra learned sharpening layer was trained for 6,000 of 10,000 planned steps, added 2.3-3.3 ms per frame and still lost to plain sharpening.
- PSNR does not track LPIPS here: it favours the 256 px core on average (27.4 vs 26.3 dB), driven by the training avatar, while the 512 px network wins on avatar 5 (25.0 vs 24.5 dB). We rank by LPIPS.
- Speed, headless on a P100: 19.5-19.8 ms per frame for the 256 px core and 35.3-36.1 ms for the 512 px network. This is one run per avatar on a shared host, with no sign of interference. The frame budget at 25 fps is 40 ms.
- The 512 px network would fit the budget on a P100 but leaves little room, which matches what was seen on the M4: lag at 512, smooth at 256. Measured on the M4 (fp16, avatar 9, one run): the 256 px core takes 13.2-14.9 ms per frame at full rate, of which the network is 10.0 ms, and skips no frame slots when paced at 25 fps; sharpening adds no measurable time (15.3 ms, 0 skipped). The 512 px network takes 40.2 ms per frame, of which the network alone is 34.6 ms, and skips 38% of frame slots at 25 fps (42% with sharpening). Every option's page output matches its PyTorch version to at least 54 dB.
- Feeding a network a splat at a resolution other than the one it was trained on scored worse in a first test (not yet verified), so splat resolution is not a free lever without retraining.

**Fixed memory per user with browser rendering: confirmed for live sessions, about 4.7-4.8 GiB per process and flat over time. Ended sessions, however, were never freed; that leak is found and fixed. One A100-80GB holds 12 users as one process per user with headroom, 16 at the limit; one shared process holds only 2, 3 at the edge.**

- Pass criteria: pooled per-chunk latency p90 under 1 s, under 1% of frames arriving more than 80 ms after their audio, and under 1% audio underrun.

| per A100-80GB, server runs motion only | sessions | chunk p50 / p90 | worst session p90 | GPU busy | GPU memory |
|---|---|---|---|---|---|
| one process per user | 12 | 430 / 505 ms | 521 ms | 87% | 56.9 GiB |
| one process per user | 16 | p90 908 ms | 969 ms | 98% | 75.6 GiB |
| one shared process | 2 | p90 356 ms | | | |
| one shared process | 3 | p90 973 ms | 1,003 ms | | |
| one shared process | 4 | p90 about 43 s | | | |

- 12 per GPU had 0% late frames and 0% underruns. It is one 10-minute run with an 8-minute steady window, not repeated.
- 16 per GPU passes the latency test with only 9% headroom and no memory headroom. It ran on a different node, and the late-frame share was not measured validly in that run.
- In one shared process the model's own compute time per chunk jumps from 91 ms (median) at 2 sessions to 462 ms at 3, and 4 sessions fail outright. Hiding the diagnostics panels still fails at 4 (p90 10.6 s), and so does leaving torch's thread count uncapped. The limit is the single Python process, not the GPU. The synthetic runs reported on 2026-10-22 put this ceiling at 8-9, without the app's per-session work; see section 3.
- The leak: in every run, every ended session's pipeline stayed in memory (for example 326 created, 326 still alive). Each held about 8.3 MiB of GPU memory, measured on sessions that barely started, so a real session may hold more. Under the churn test, processes failed with "Too many open files" after about 320-330 ended sessions.
- The cause: Streamlit forgets a disconnected session after a timeout without shutting it down, and a background thread kept the forgotten session, and with it the pipeline, reachable. The app also orphaned a pipeline when Streamlit interrupted the step that stores it.
- The fix: the app now shuts down disconnected sessions before Streamlit forgets them. In reruns of 37 to 277 sessions every pipeline was freed at the end, and open files and GPU memory returned to idle. Changing the avatar mid-session keeps the stream alive. Part of the fix is a garbage collection pass that briefly pauses the server, so it is held off while any session is playing and forced only after 10 min of deferral.
- What remains: small objects still accumulate in aiortc's media relay until a fix lands upstream.
- The latency numbers from the churn runs are invalid because of a harness bug, now fixed. A churn rerun on the fixed app is needed before quoting latency under session turnover.

**AI-generated label: implemented in both render modes.** A visible "AI-generated" badge is drawn into the avatar image itself: into the server-rendered frames, so it survives screen recording and the video stream, and onto the browser canvas in browser-rendering mode. A short caption next to the avatar says the same. The badge costs at most 0.1 ms per frame on the server. It is a text badge; a logo can replace it if the team provides one. Research runs can turn it off with `ARTALK_AI_BADGE=0`.

**Voice upload and cloning: not attempted.** It remains future work.

## 2. Other work since 2026-10-28

- The browser renderer is now part of the main app behind the `--client-render` option, which stays off by default.
- The browser renderer relied on ONNX Runtime Web reusing preallocated outputs in a captured session, which the runtime only recognises on the first run; it worked by chance. The renderer now depends on a patched runtime. Existing renderer bundles must be re-exported once with `artalk-demo client-ort --client-render-dir <dir>`.
- Security fixes from an audit of the public page:
  - The Custom endpoint option sent the server's OpenAI key to whatever address a visitor typed. It no longer does.
  - Visitor-steerable server connections (the Custom endpoint and PersonaPlex addresses), the diagnostics snapshot button and profiler traces are off on public deployments. They need the operator option `--operator-tools`, which is off by default.
  - Error messages and events shown on the page are scrubbed of server internals, tracebacks go only to the server log, and the server no longer shows key status banners to visitors.
  - Diagnostic dumps written to disk are capped, so visitors cannot fill the disk.
- When a source track outlives its pipeline (for example after an avatar change), the stream now receives a blank frame instead of stopping.
- The app now opens on a GAGAvatar face instead of the mesh.
- Face-to-audio sync in browser-rendering mode: aligning each motion frame to the audio by RTP timestamps instead of by arrival time. In a headless test on Linux the face was 14 ms off the audio with RTP timing against 38 ms with the current method. With 150 ms of added delay on the motion data, the offset was 8 ms with RTP timing against 93 ms with the current method. The browser can also hold audio briefly when motion data runs late. Both are selectable options. Compared by eye on the M4 with Bluetooth headphones, the two looked very similar, RTP timing perhaps slightly better; the browser reported only 30-42 ms of output latency, so the extra delay Bluetooth adds is invisible to both methods and is the likely remaining error.
- Running the motion model in the browser as well (on the M4, fp16, one run each): a 1 s chunk took 210 ms at the median with the renderer running, well inside 1 s. Splitting the motion work between rendered frames brought the renderer's extra skipped frame slots to 0, with a chunk p90 of 343 ms. The server would then only hold the FLAME model and stream mesh vertices.

## 3. Corrections to the 2026-10-22 status

- "Motion-only sessions: 8-9 per A100 in one process": that came from a synthetic harness without the app's per-session work. The real app in browser-rendering mode holds 2 sessions per process, 3 at the edge. The one-process-per-session figure holds up: 12 sustained and 16 at the limit, against 16 (memory-bound) before.

## 4. Open questions / proposed next directions

1. Resolution per device: the sharpened 256 px core by default; an M4-class laptop stays on it. The sharpened 512 px network is only worth offering on clearly faster GPUs, picked by a short startup probe (proposed: a median of at most 26 ms and a p90 of at most 30 ms per frame); that threshold still needs a measurement on such a GPU.
2. Capacity: plan on 12 users per A100-80GB, as one process per user. The app does not yet spread visitors over several processes, so serving that many needs a front that assigns each visitor to a process. A 24 GB GPU is untested.
3. Leak follow-up: offer the streamlit-webrtc and aiortc fixes upstream, which also removes the residual growth in aiortc's relay; rerun the churn test on the fixed app for latency under session turnover (about 1.3 A100-hours).
4. Which built-in avatars public deployments should offer, now that the operator can restrict the list.
5. Sync: make RTP timing the default once the audio hold ignores the gap at session start; add a per-device audio delay setting for Bluetooth listeners, since browsers cannot see that delay.
6. Voice labels: keep the providers' descriptions, or add labels chosen by the team for the voices that have none.
